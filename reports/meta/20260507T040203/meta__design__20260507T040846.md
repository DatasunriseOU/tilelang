## Finding 1
- **Severity**: high
- **File**: `src/op/copy.cc:581`
- **Issue**: Z3 query uses hardcoded CUDA H100 virtual-address envelope `addr < 2^48` and `stride < 2^48`. This couples the legality check to a specific GPU architecture. For non-Hopper GPUs, mixed-target compilation, or future devices with larger VA space, the check becomes unsound: it will reject valid TMA if the runtime address/stride >= 2^48, or worse, accept invalid cases if the limit changes. The 48-bit constant is a leaky abstraction - Z3 should only enforce `addr % 16 == 0`, not guess hardware VA limits. 
- **Fix**: Remove the VA-range constraints entirely. Replace lines 575-580 with only alignment goals: `PrimExpr goal = (FloorMod(addr_bytes, IntImm(DataType::Int(64), 16)) == IntImm(DataType::Int(64), 0) && (FloorMod(stride_bytes, IntImm(DataType::Int(64), 16)) == IntImm(DataType::Int(64), 0));` If a range bound is required by Z3 for termination, expose it as a target attribute instead of hardcoding 2^48.

## Finding 1
- **Severity**: high
- **File**: `src/transform/vendored/z3_prover.cc:L161-L165`
- **Issue**: The fix for C8 correctly avoids Z3 silent truncation in `MakeIntVal` by minting an unconstrained symbol when `value` is out of signed BV range. However, the same guard is missing in `MakeUIntVal`. If a `uint64` literal > `2^width-1` is passed while `bv_width_ > 0`, Z3’s `bv_val(uint64_t, width)` will still truncate silently. That breaks the “no silent wrap” guarantee C8 established for signed paths. `MakeUIntVal` is used for `uint64` dtype bounds `src/transform/vendored/z3_prover.cc:L167-L169`, so the risk is live for `uint64` constants.
- **Fix**: Mirror the C8 range check in `MakeUIntVal`. Compute unsigned upper bound ` (1ULL << width) - 1 `. If `value > upper`, log once and return `MakeIntConst("oor_u_" + ...)`. Else call `ctx->bv_val(value, width)`.

## Finding 2
- **Severity**: medium
- **File**: `src/transform/vendored/z3_prover.cc:L194-L205`
- **Issue**: `EnterConstraint` now snapshots `side_effect_exprs_` and captures by value in the recovery lambda. Good. But the snapshot is taken *before* `solver.add(VisitBool(constraint))`. If `VisitBool` throws while evaluating the constraint, the exception propagates out of `EnterConstraint`, the lambda is never returned, and `side_effect_exprs_` never gets erased from `memo_`. The prover’s memo then contains stale entries that reference expressions from a failed/rolled-back constraint scope. Next proof attempt will reuse wrong z3 exprs.
- **Fix**: Wrap the `solver.add(VisitBool(constraint))` in try/catch. On exception, erase all exprs in the local `side_effect_exprs` from `memo_` before rethrowing. Or move the snapshot after a successful `add`, but then you’d miss side-effects created during constraint conversion. Safer: RAII guard that erases on scope exit.

## Finding 3
- **Severity**: medium  
- **File**: `src/transform/vendored/z3_prover.cc:L265-L275`
- **Issue**: C6 fix for `Ramp` returns unconstrained `MakeIntConst`. That is sound, but it loses all lanes. Downstream passes that rely on contiguity proofs for vectorized loads will now fail to prove where previously they might have succeeded via base-only approximation. There’s no extension point to plug in a lane-aware model. The visitor hard-codes “unconstrained” with no policy hook. Over-engineered in one direction: we’ve taken the most conservative step without a way to opt into “unsound-but-useful” models for specific passes.
- **Fix**: Add a policy knob on `Z3Prover`: `enum RampModel { kUnconstrained, kBaseOnly, kPerLane }`. Default to `kUnconstrained`. Passes like `LoopVectorize` can set `kBaseOnly` when they know they only care about lane 0. Make the visitor switch on the policy. This gives an extension point without sacrificing soundness by default.

## Finding 4
- **Severity**: medium
- **File**: `src/transform/vendored/z3_prover.cc:L370-L376`
- **Issue**: C5 fix for `Bind(var, Range)` with empty range `min >= max` now does `solver.add(false)` and memos the var. Sound, but the empty-range case is also used to model dead code. `solver.add(false)` makes the *entire* current solver state UNSAT, not just the branch. If this bind happens inside a larger scope, all subsequent `CanProve` calls will trivially return true because the context is contradictory. That’s correct for “unreachable code” but leaky: the caller has no way to distinguish “proved” vs “context is already unsat”. Better to model empty range as a fresh unconstrained var with no constraints, or push a scoped `false` and pop immediately.
- **Fix**: For empty ranges, skip adding `false` to the main solver. Instead, memoize the var but add no constraint, or create a nested `solver.push(); solver.add(false); solver.pop();` just to validate. Don’t pollute the live context. Add a comment that empty range = dead code, not provable property.
