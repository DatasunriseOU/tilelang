- **Issue**: Integer range used for CUDA address/stride proof uses `int64_t{1} << 48` as upper bound. ## Finding 1
- **Severity**: critical
- **File**: `tilelang/transform/metal_fragment_to_simdgroup.py:101`
- **Issue**: Z3-based simdgroup eligibility bypasses address alignment check. `_z3_simdgroup_eligible` constructs `addr_clause` string but never sends it to a solver. For symbolic shapes, the function returns `False` early, but when shapes are static `IntImm` and `addr_value` is provided, it returns `True` after only checking `addr_value % addr_align_bytes` locally. However the public wrapper `is_simdgroup_eligible` never passes `addr_value`, so `addr_align_bytes` check is unconditionally skipped: line 155 calls `_z3_simdgroup_eligible(shape, dtype)` with no addr. Thus any buffer with static shape multiple of 8 and approved dtype is marked eligible even if base address is provably unaligned. If `PassConfig["tl.simdgroup_matrix_rewrite"]` is enabled, line 215-219 will promote such buffers to `metal.simdgroup` scope, causing `codegen_metal.cc` to emit `simdgroup_load` which requires 16-byte alignment per Metal spec. Attacker-controlled symbolic indices that resolve to unaligned addresses at runtime will trigger GPU memory faults or out-of-bounds reads in simdgroup intrinsics, a memory safety violation exploitable for information leak or DoS.
- **Fix**: Either: 1) Remove Z3 path entirely since it’s non-functional, or 2) Propagate actual base address TIR expr to `_z3_simdgroup_eligible` and add constraint `addr % 16 == 0` to a real Z3 query. At minimum, change line 155 to: `proved, query = _z3_simdgroup_eligible(shape, dtype, addr_value=None)` and refuse eligibility when base address cannot be proven aligned. For static path, add alignment check using `buf.data_alignment` or `buf.elem_offset` before returning True.

## Finding 2
- **Severity**: high  
- **File**: `tilelang/transform/metal_simd_lift.py:273`
- **Issue**: Integer overflow in butterfly stage calculation. `_butterfly_stages` computes `n_stages = int(math.ceil(math.log2(extent)))` then `top = 1 << (n_stages - 1)`. For `extent > 2**31`, `n_stages-1 >= 31`, so `1 << 31` overflows Python int to long, but subsequent `while s >= 1: out.append(s); s //= 2` will produce shifts like 2147483648, 1073741824… all `>= 32`. The assert at line 289 `assert 1 <= shift < 32` will fire, but only after attacker supplies a loop with symbolic extent that later constant-folds to >32. If TVM constant propagation or `tir.IntImm` with int64 is used, this becomes a panic DoS in the compiler. More severe: if assert is compiled out with `-O` or Python `-O`, invalid `mask` values reach `_build_butterfly` and are emitted to `tl.shfl_xor_sync(mask, ...)`. Metal spec requires `simd_shuffle_xor` offset `< 32`; out-of-range causes undefined behavior, potentially reading other lanes’ registers.
- **Fix**: Add explicit guard before shift generation: 
```python
if extent > _SIMD_LANES or (extent & (extent - 1)) != 0:
    raise ValueError(f"simdgroup extent {extent} must be pow2 <= 32")
```
Place this at start of `_butterfly_stages`. Also change assert to hard error, not Python assert.
