### **Design/Architecture Issues — The Real Problems**

**1. Violated abstraction: `fx_to_tilelang.py` owns too much**  
File is 2289 lines. Line `:1715` shows it’s doing grid calc, which belongs in a `LaunchConfig` class. You’ve coupled FX pattern matching, TileLang codegen, and CUDA launch param heuristics in one module.  
**Simplify**: Extract `class LaunchPlanner` with `plan_matmul(shape) -> Grid,Block`. FX pass just emits HLO; planner decides `block_M/N/K`. Extension point: add `register_heuristic(op, fn)` so DSA vs GEMM vs conv don’t edit core.

**2. Leaky module: `custom_op_wrapper.py` knows about cache policy**  
Line `:238` returns `_bind_runtime` which presumably memoizes. That couples the op registration to runtime artifact caching. If you swap Triton for CUTLASS, you edit this file.  
**Fix**: Inject `ArtifactCache` protocol. `def register_op(..., cache: ArtifactCache = DefaultLRU())`. Now tests can pass `NullCache` and you don’t flush global state.

**3. Duplicated logic: ceildiv everywhere**  
`fx_to_tilelang.py:1715` uses `T.ceildiv`. `dsa_splitk_indexer_loss.py` likely reimplements it. You have 3 versions: Python `//`, `triton.cdiv`, `T.ceildiv`.  
**Action**: Single source: `from tilelang.utils import cdiv` and delete others. Mismatched rounding caused the int32 overflow.

**4. Missing extension point: reduce ops**  
`reduce_op.py:38` comment: `ceil(N/batch) batched AllReduce`. Hard-coded to NCCL. No way to plug in RCCL, UCC, or single-node reduce without forking.  
**Suggest**: `class ReduceBackend(Protocol): def allreduce(tensor, op): ...`. Register `NCCLBackend`, `RCCLBackend`. `reduce_op.py` just dispatches.

**5. Over-engineering: `_FP8_AMAX_LOCK` vs per-device streams**  
If amax is per-CUDA-stream, a global Python lock serializes all devices. On 8xH100 you just lost 8x throughput.  
**Design**: `locks = defaultdict(threading.Lock)` keyed by `tensor.device`. Or better: remove lock, use `torch.cuda.current_stream().wait_stream()` if you need ordering.

**6. Naming/clarity: `lower_tma_to_ptr_arith.cc:38`**  
Comment says `InjectSoftwarePipeline already runs`. That’s a lie if someone disables the pass. Comments that assert global invariants are code smell.  
**Rule**: Comments describe *this* unit. Global context goes in `docs/architecture.md`. Replace with: `Assumes software pipeline has inserted mbarriers.`

### **4th Category Bug All 3 LLMs Miss: Determinism Under Autocast**

None of your wave-1-to-9 fixes check `torch.is_autocast_enabled()`. Path:  
1. User runs model under `torch.autocast(dtype=torch.bfloat16)`
2. Your fused kernel sees `fp32` inputs from FX graph, but `autocast` context downcasts to `bf16` mid-kernel if you call any ATen op inside TileLang host code.
3. `fp8_amax` returns `fp32` amax, but subsequent `quantize` expects `fp32`. If `autocast` is on, it gets `bf16` amax -> `quantize` silently loses range -> 2% accuracy drop.

All 3 LLMs miss this because tests run eager, not under `autocast`. Grok/chatgpt/meta won’t invent that context.

**Fix**: In `custom_op_wrapper.py`, wrap `_impl` with `@torch.no_autocast()` or explicitly cast: `amax = amax.to(torch.float32)` before quantize. Add pytest: `with torch.autocast('cuda', torch.bfloat16): loss = model(x)`.
