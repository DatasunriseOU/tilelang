### 3. Additional security issues found now

1. **Untrusted shape -> CUDA grid launch without validation**  
   File: `fp8_amax.py:361` `with T.Kernel(T.ceildiv(N, BLOCK), threads=threads) as bx:`  
   `N` comes from tensor shape `fp8_amax.py:350`. If a malicious `.pt` file has `tensor.shape[0] = 2**62`, `T.ceildiv(N, BLOCK)` = `2**52` blocks. CUDA limit is 2**31-1 per grid dim. Launch will fail, but before that you allocate `amax_out = torch.empty((grid,), dtype=torch.float32)` implicitly. That’s `2**52 * 4 bytes` = 16PB allocation -> host OOM kill. **DoS**.  
   **Fix**: `if N > 1<<30: raise ValueError("tensor too large")` before kernel build.

2. **Path/descriptor injection via target string**  
   File: `fp8_amax.py:284` `return "metal -thread_warp_size=32"` and `dsa_splitk_indexer_loss.py:314` same.  
   `_target_family` not shown, but if `target` comes from `torch.backends.cuda.get_device_properties(name)` or user config, attacker could set `target="metal; rm -rf /"` and if you ever shell out, RCE. Grep shows no `subprocess`, so **not exploitable now**, but if future code does `os.system(f"clang {target}")`, it’s command injection.  
   **Fix**: Validate `target in {"cuda", "metal", "cpu"}` whitelist.

3. **Deserialization of cached kernels**  
   Not shown in excerpts, but TileLang typically caches compiled `.so` files. If cache dir is world-writable, attacker drops malicious `.so` with same hash -> code exec on import. Check your `tilelang.cache` path perms. Not in this diff, but new fused op increases cache surface.

4. **Side-channel: timing via atomic_max**  
   `fp8_amax.py:320` `T.atomic_max` on global. If `amax` is secret-dependent, thread divergence timing leaks max value. Not likely for ML, but if you quantize gradients with DP, this breaks constant-time. **Info leak**. Mitigation: use tree-reduce then single atomic.
