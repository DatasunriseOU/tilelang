### **2. Wave-10/wave-11 backlog still open**

1. **Lock-DoS (3c)** `fp8_amax.py`  
   Status: Acknowledged, wave-12. **Design root cause**: Globals are a layering violation. TIR script should be pure. You’re doing JIT + autotuning in the same module that defines the kernel.  
   **Simplify**: Split `fp8_amax.py` into `fp8_amax_tir.py` = pure TIR, and `fp8_amax_compile.py` = caching/locking. No globals. Pass `N,BLOCK,DTYPE` as args, not module state. Then the per-sig lock is trivial.

2. **reduce_prod runtime fix vs static_assert** `reduce.h`, `reduce.cc`  
   **Awkward coupling**: You have a compile-time `static_assert` but `reducing_threads` can be dynamic in AutoTVM/Ansor. The `ICHECK` only fires in `MakeInitValue`, but if the scheduler sets `reducing_threads=12` after lowering, you compile garbage.  
   **4th-category bug**: Boundary assumption: “reducing_threads is known at Lower time”. In practice, MetaSchedule can rewrite it post-Lower.  
   **Fix**: Make `reducing_threads` a PrimFunc attr. Validate once in `VerifyMemory` pass. Remove checks from headers. If you must keep the header assert, make it `if constexpr(reducing_threads > 0) static_assert(is_pow2(reducing_threads))` so dynamic values bypass it and hit runtime path.

### **3. New 4th-category bugs all 3 LLMs would miss**

These are “boundary assumption” bugs where two modules agree on a contract that the ecosystem violates.

1. **TIR → Metal: `T.atomic_max` with fp8** `fp8_amax.py:386`  
   **Assumption**: “Metal has atomic_max for all types we lower to.”  
   **Reality**: Metal 3.0 only has `atomic_max` for `int`/`uint`. For `half`/`float` you must emulate with CAS loop. For `fp8` you’re relying on TVM promoting to `half` first. If future TVM skips promotion, you’ll codegen `atomic_max_e8m0` and Metal rejects it.  
   **Attacker**: Pass `dtype="e4m3"` on Apple M3 with TVM `fp8_promotion=none`. Build succeeds, runtime `MTLCompilerError`.  
   **Fix**: Extension point: `target.supports_atomic(dtype)` query in TIR. If false, TIR should insert CAS loop or refuse. Don’t leak Metal ISA into `fp8_amax.py`.

2. **DSA indexer + TorchDynamo graph breaks** `dsa_splitk_indexer_loss.py`  
   **Assumption**: `_detect_storage_overlap()` runs before Dynamo tracing.  
   **Reality**: Dynamo traces the function, sees `as_strided`, and may constant-fold it away. Your overlap check never runs in the traced graph, but runs in eager, causing train/eval divergence.  
   **Attacker**: `torch.compile(model)` → NaNs in prod, fine in unit tests.  
   **Fix**: Make the check a `torch._dynamo.disallow_in_graph` function or move it to a `__torch_dispatch__` wrapper. Don’t do data-dependent checks in code Dynamo will trace.

3. **reduce.h: `reducing_threads` vs warp shuffle** `reduce.h`  
   **Assumption**: `reducing_threads <= 32` so one warp.  
   **Reality**: User can set `reducing_threads=64` on MI300. Your `__shfl_down_sync` tree only handles 32-wide. For 64 you need 2 warps + shared mem. `static_assert` catches it, but the header name `reduce.h` implies it’s generic.  
   **Naming/clarity problem**: Rename to `warp_reduce.h` or add `static_assert(reducing_threads <= warpSize)`. Current name leaks that it’s not a general reduce.
