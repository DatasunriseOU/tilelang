### 2. Wave-10/11 backlog still open

**1. _FP8_AMAX_LOCK DoS - HIGH, still open, wave-12 only**  
`/mnt/data/fp8_amax.py:78-84`, `/mnt/data/fp8_amax.py:98-100`  
Global lock still serializes all unique `(n, dtype)` compiles. Module globals `N, BLOCK, DTYPE, FP8_MAX` are mutated by `/mnt/data/fp8_amax.py:376` under lock.  

*Concrete attacker scenario*: Multi-tenant inference server. Tenant A spams `fp8_amax_tilelang(torch.randn(n))` with `n=1025,1026,...2048`. Each misses cache, acquires `_FP8_AMAX_LOCK` for 50ms JIT. 1000 req/s = 50s of serialization. Tenant B’s legit requests stall, SLO breach. This is a trivial slowloris. No auth needed - just shape variety.  

*Why per-signature lock fails*: `/mnt/data/fp8_amax.py:81-85` comment is correct. Two threads: T1 compiles `(1024,fp16)`, T2 compiles `(2048,bf16)`. If each has own lock, both write `globals()["N"] = ...` unsynchronized. TileLang’s `@T.prim_func` parser reads `N` during decoration and gets wrong value -> wrong `T.Tensor((N,), DTYPE)` shape -> segfault.  

*Fix path*: Wave-12 plan in `/mnt/data/fp8_amax.py:92-94` is right. Move `N/BLOCK/DTYPE` to `T.Var` params. Then delete `_expose_to_globals` and the global lock. Until then, this is a production DoS.

**2. reduce_prod runtime fix vs static_assert - MED, still open**  
`/mnt/data/reduce.h:185-187`, `/mnt/data/reduce_b39d70.h:119-120`  
`static_assert((threads & (threads - 1)) == 0)` is compile-time only. If `reducing_threads` comes from a TIR var, not const, compiler can’t eval. TileLang will emit kernel with wrong `threads`, then `__shfl_xor_sync` runs with non-pow2 mask. On H100, `__shfl_xor_sync(0xffffffff, val, 24)` with 48 active threads reads from lane 24+32=56 -> out of warp -> undefined.  

*Attacker scenario*: TorchDynamo captures graph with symbolic `s0`. TileLang specializes to `s0=48` at runtime. Lowering emits `AllReduce<..., 48, ...>`. Compiles fine because `threads` is template but not static_asserted against runtime value. Kernel launch -> garbage results, no crash. Silent corruption.  

*Fix*: Add runtime `assert(__popc(active_mask) == 1 << __ffs(active_mask-1))` in CUDA path, or assert in host launcher before kernel.  

### 3. New 4th-category bug all 3 LLMs would miss: "Boundary assumption" in CumSum2D

**File: `/mnt/data/reduce.cc:857-860`, `/mnt/data/reduce.h:261-264`, `/mnt/data/reduce_b39d70.h:174-177`**  

The `CumSum1D` and `CumSum2D` templates have `static_assert(threads == 1024 or 512 or 256 or 128 or 64 or 32)`. But `threads` is the *blockDim.x*. The actual per-warp reduction uses `SEG=32` on CUDA, `SEG=64` on HIP.  

*Bug*: If `N < SEG` and `reverse=True`, `/mnt/data/reduce.h:280-282` calculates `num_segments = (N + SEG - 1) / SEG = 1`. Loop `for (seg = num_segments-1; seg >= 0; --seg)` runs once with `seg=0`. Inside, `idx = seg*SEG + lane = 0*32 + lane`. For `N=1`, only `lane=0` has `idx < N`. It loads `src[0]`, others load `0`. The prefix op then does `__shfl_up_sync` across 32 lanes. Lane 0 gets correct sum. Lanes 1-31 get `carry` propagated from lane 0, but they never write because `idx < N` is false.  

*Security impact*: Benign for `CumSum` alone. But if caller uses `dst` as input to subsequent `ReduceOp` with `reducing_threads=32`, lanes 1-31 contain `carry` from lane 0, not identity. If `ReduceOp` is `SumOp`, result is `N*src[0]` instead of `src[0]`.  

*Attacker scenario*: Model fuses `cumsum(x[:1]) -> reduce_sum`. Attacker sets `x=`. Expected sum = `1e38`. Actual: thread 0 writes `1e38`, threads 1-31 write `1e38` too. `AllReduce<SumOp,32>` gives `32*1e38 = inf`. Loss becomes `inf`, gradients NaN, training crashes. This is a data-dependent DoS.  

*Why LLMs miss*: Requires tracing `SEG` constant, `num_segments` ceil-div, and interaction with `AllReduce` identity rules. 4th-category "cross-template invariant".  

*Fix*: In `CumSum1D::run`, after `__shfl_up_sync` loop, add `if (idx >= N) val = T(0);` before `dst[idx] = val`. Or mask `carry` update with `if (seg*SEG + SEG-1 < N)`.  

*Test gap*: No test where `N < SEG` and `reverse=True` and output feeds `reduce_sum`. Add `test_cumsum_reverse_N1_then_sum()`.

### 4. Security vulnerabilities still present

**1. Host OOB in IndexMask load - MED, tainted-data flow**  
`/mnt/data/dsa_splitk_indexer_loss.py:529-533`  
Comment says "Guard the IndexMask load against OOB", but code uses `if valid: s = scores_f[i,j] * SCALE + IndexScores[...]`. TileLang may speculatively execute both branches before predicate. If `IndexScores` is out-of-bounds due to `topk_indices` corruption, speculative load triggers ASAN/UBSAN. On CUDA, `__ldg` to OOB is undefined per PTX.  

*Attacker scenario*: Attacker controls `topk_indices` via checkpoint. Sets `topk_indices[0,0,0] = 1e9`. Bounds check `/mnt/data/dsa_splitk_indexer_loss.py:1388-1393` uses `.max().item()` which syncs, but if attacker also sets `sparse_loss=False`, check is skipped. Kernel runs, speculative load hits OOB, CUDA context corruption.  

*Fix*: Use `T.if_then_else(valid, IndexScores[...], -inf)` instead of `if valid:` to prevent speculative load.

**2. Integer overflow in _q_cache_bytes - LOW, but DoS**  
`/mnt/data/dsa_splitk_indexer_loss.py:678-680`  
`return BLOCK_SQ * AH * AD * dtype_bytes`. No overflow check.  

*Attacker scenario*: Call with `BLOCK_SQ=65536, AH=65536, AD=64, fp16`. Product = `65536*65536*64*2 = 549.8GB`, but overflows 32-bit int to `0`. `/mnt/data/dsa_splitk_indexer_loss.py:704` compares `0 <= budget`, returns `True`. Allocates 0-byte `Q_all_heads`, then `/mnt/data/dsa_splitk_indexer_loss.py:982-983` writes `Q_all_heads[h, i, dd]` -> heap buffer overflow.  

*Fix*: Use `math.prod` with Python ints, or `if BLOCK_SQ > 65535 or AH > 65535: return False`.

**3. Tensor dtype confusion - MED**  
`/mnt/data/fp8_amax.py:568-571`  
`_resolve_in_dtype` only allows `float16, bfloat16, float32`. But `/mnt/data/fp8_amax.py:380` casts to `T.Tensor((N,), DTYPE)`. If attacker passes `torch.int32` tensor, hits `TypeError`. But if attacker registers new torch dtype that passes `is_floating_point=False` but has `__torch_dtype__ = "float16"`, bypasses check. TileLang casts int32 bit-pattern to fp16, producing garbage `amax`. Downstream `inv_scale = 448/1e-8 = 4.48e10`, quantizes to all `0x7F`.  

*Attacker scenario*: Supply chain attack on `torch` fork. Add `torch.custom_float`. `fp8_pack_tilelang` accepts it, corrupts weights, causes model to output attacker-controlled tokens.  

*Fix*: Check `tensor.dtype.is_floating_point` not just dict lookup.
