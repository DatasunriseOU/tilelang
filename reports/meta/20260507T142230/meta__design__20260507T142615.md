### **Wave-10 Fix Verification**

#### **1. DSA zero-size guard: commits aef3b2f + 3d5ec05**
**Claim**: Closes `ASq=0` div-by-zero, consensus HIGH  
**Verification**: `dsa_splitk_indexer_loss.py`  
**Finding**: Line 47-52 implements `if ASq == 0: return fallback_indexer`. That directly prevents the div-by-zero in the stride calc at line 78 `stride = total / ASq`. No new regression: fallback path uses contiguous indexer, which preserves semantics for empty K-slice.  
**Design issue**: `dsa_splitk_indexer_loss.py:47` The zero-guard is buried inside the indexer factory. This is **leaky abstraction**. Callers of `make_dsa_indexer` shouldn't need to know that `ASq=0` is special. Better: assert upstream when building the split-k schedule, or make `ASq` a `NonZeroInt` type. Guarding at use-site means every similar kernel needs its own check.  
**Actionable**: Move the guard to `SplitKSchedule.validate()` instead of `dsa_splitk_indexer_loss.py:47`. One check vs N checks.

#### **2. TMA i64: commit 4d180941, wave-3 340439d6**
**Claim**: Meta's CRITICAL was false-positive, i64 already in tree  
**Verification**: `lower_tma_to_ptr_arith.cc`  
**Finding**: Line 134-141 `if (isa<IntegerType>(offset.getType()) && offset.getType().getIntOrFloatBitWidth() == 64)` handles i64. The meta complaint was stale. However, line 128 `auto stride = rewriter.create<arith::IndexCastOp>` unconditionally casts to index.  
**Design issue**: `lower_tma_to_ptr_arith.cc:128-135` **Abstraction violation**. TMA descriptor lowering should not know about `index` vs `i64`. You’re doing ptr arithmetic in the TMA pass. The lowering pass should emit `tma.load` ops with i64 offsets, and a separate `memref-to-llvm` pass should do the cast. Right now you’ve coupled TMA semantics to LLVM ptr width.  
**Actionable**: Delete lines 128-135. Change TMA op to accept `i64` offset natively. Let the final lowering decide index width. Extension point missing: no way to target 32-bit TMA HW later.

#### **3. reduce_prod warp mask: cf25c0e1, doc-only + xfail test**
**Claim**: Caller-pad-to-1.0 contract documented in `reduce.h`, xfail for non-warp-divisible N  
**Verification**: `reduce.h` and `reduce_op.py`

**Design issue 1**: `reduce.h:89` **Leaky module**. The contract "pad to 1.0" belongs to the *producer* of the reduction, not the reduction itself. A reduction op should be self-contained. You’ve pushed a correctness requirement to all callers. That’s the definition of awkward coupling.  
**Design issue 2**: `reduce_op.py:210` xfail test proves the contract is not enforced. Tests that xfail are documentation, not safety. This is **under-engineering** of a correctness property. Silent NaN is still possible today if a caller forgets.  
**Verdict**: No, the documented contract is **not sufficient** to prevent silent NaN attacks. Doc comments are not control flow. Any new kernel author will miss this. You need a mechanical check.  
**Actionable**: `src/op/reduce.cc:MakeInitValue` in wave-11 is the right fix. Interim: add `assert N % warp_size == 0 || op != ReduceProd` in `reduce.h:102` debug build. Fails fast vs silent NaN.

### **4th-Category Bugs All 3 LLMs Miss**

These are design bugs that single-file reviewers miss because they require cross-file context:

1. **Inconsistent error-handling philosophy**  
   `dsa_splitk_indexer_loss.py:47` returns fallback on bad input. `lower_tma_to_ptr_arith.cc:141` does `assert(false)` on bad type. `reduce.h:89` uses documentation. One codebase, three strategies: forgive, crash, ignore.  
   **Impact**: New contributors can’t predict what happens on edge cases.  
   **Actionable**: Pick one. For compiler IR, assert/fail-fast is standard. Change DSA path to `assert ASq > 0`. Delete the fallback. Failures should happen during graph construction, not kernel launch.

2. **Naming/clarity: `lower_tma_to_ptr_arith.cc` lies**  
   The file is named "lower_tma_to_ptr_arith" but line 1-200 don’t lower TMA to ptr arithmetic. They lower TMA to `llvm.call_intrinsic`. The actual ptr arithmetic is lines 128-135, which we said should be deleted.  
   **Impact**: Future devs looking for ptr arithmetic logic will open this file and find the wrong thing.  
   **Actionable**: Rename to `lower_tma_to_llvm.cc`. Or split: `tma_legalize.cc` + `ptr_arith_pass.cc`.

3. **Missing extension point: fp8 recipe**  
   `fp8_amax.py:35` hardcodes `e4m3fn` and `amax_history_len=16`.  
   **Design**: No way for a model to use `e5m2` or per-channel amax without forking the file. You’ve under-engineered the config surface.  
   **Actionable**: `class Fp8Config(NamedTuple): fmt: DType, amax_len: int`. Pass it into `quantize()`. Now you can A/B test recipes without code changes.
