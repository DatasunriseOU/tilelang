**Why doc-only is insufficient**: This is a TOCTOU-style bug at the compiler IR boundary. Security boundary = Python/Torch frontend → TileLang codegen → PTX. The frontend can’t enforce the contract. If a user writes:

```python

```

TileLang lowers to `warp_reduce<MulOp>` with 32 lanes. Lanes 30,31 read uninitialized shared mem. If that memory had 0x0 from prior kernel, product=0. If it had NaN, product=NaN. **Data corruption, not just crash.**

**Attack scenario**: Adversary in multi-tenant GPU cluster submits model with `reduce_prod` over dim=30. Your kernel runs after a kernel that left NaN/0 in smem. **Verdict**: Doc+test helps developers, but doesn’t stop malicious/oblivious codegen. **NOT FIXED.** See #2.

### 2. Is the documented contract sufficient to prevent silent NaN attacks today?

**No.** `reduce.h:52-65` comment is a seatbelt sign with no seatbelt. Reasons:

1. **No static enforcement**: `reduce_op.py:36-48` accepts any shape. Nothing in TileLang IR validates `N % 32 == 0` for `reduce_prod`.
2. **Runtime UB**: Warp shuffle reads garbage. CUDA spec: “behavior undefined if thread inactive”. On NVIDIA, you get lane’s register. On AMD, you can get 0. Divergent behavior = fingerprinting.
3. **Test is xfail**: `xfail test for non-warp-divisible N` means CI is green but prod still vuln.

**What wave-11 MUST do**: In `src/op/reduce.cc:MakeInitValue`, emit:

```cpp
if (reduce_kind == Mul &&!is_divisible(N, warp_size)) {
  auto pad_val = make_const(type, 1.0);
  // predicate load: val = (tid < N)? buf[tid] : pad_val;
}
```

Until that lands, **treat `reduce_prod` as unsafe on user-controlled shapes**. Mitigation now: add runtime assert in `custom_op_wrapper.py:_ensure_contiguous_inputs` that rejects `reduce_prod` if any dim not multiple of 32. Log and drop request.

### 3. Anything from previous waves' meta findings still un-addressed?

**Yes, 2 items:**

**A. `custom_op_wrapper.py:38-55` — View-aliasing guard is best-effort, not sound**

You check `t._base is not None` to detect views. **Bypass**: `t.unfold().transpose()` creates a view where `_base` is None but storage is aliased. Also, `torch.as_strided` bypasses it.

**Attack**: Attacker passes aliased tensor to your fp8 kernel. Kernel writes to shared storage while autograd still holds ref to parent. Race on H2D memcpy. Corrupt gradients → model backdoor.

**Fix**: Use `t.storage().data_ptr()` + `t.numel()` to build interval tree of all inputs. Reject overlaps. Or deep-copy all inputs unconditionally in security-critical paths.

**B. `_FP8_AMAX_LOCK` global: DoS via lock contention**

`fp8_amax.py:38` You serialize all JIT compiles. **Attack**: Spin up 1000 threads all calling `fp8_amax_tilelang` with unique `(N, dtype)`. All block on global lock. Your inference server stalls. This is by design for correctness, but it’s a DoS amplifier.

**Fix**: Replace global lock with per-signature lock: `locks = defaultdict(threading.Lock)` keyed by `(N, DTYPE, BLOCK)`. Still serializes same kernel, allows parallel compile of different ones.

### 4. New 4th-category bugs all 3 LLMs miss together?

**Found 1: Integer overflow → OOB in TMA fallback**

`lower_tma_to_ptr_arith.cc:60-100` — You decompose TMA into nested `For` loops with pointer arithmetic. If user passes tensor with `dim[i] * stride[i] > 2^31`, the `int32` loop var overflows. On CUDA, `threadIdx.x` is int, but your generated loop uses `int` for `elem_offset`.

**Attack**: Allocate 8GB tensor, `BLOCK_SK=64`, `grid.z=2^26`. `elem_offset = blockIdx.z * BLOCK_SK * stride` overflows → negative offset → OOB global read. On H100 this is MMU fault → node reset.

**File:line**: The generated `For` from `LowerTmaToPtrArith` lacks `int64` cast. Add `tir.Cast("int64",...)` on all offset math.
