**Code Review: `poc/torch_dynamo/` POC (focus: security + bugs + perf + deliverables)**

### Security Summary (concrete attacker scenarios only)
**No material security vulnerabilities** were introduced by this diff. This is a pure compile-time lowering backend that operates exclusively on **trusted** FX `GraphModule`s produced by `torch.compile` / `aot_autograd` from user model code. There is:

- **Zero** command/template/SQL injection surface (no `subprocess`, no `eval`, no Jinja/any string templating of user data).
- **Zero** unsafe deserialization (no `pickle`, `yaml`, `torch.load` on untrusted paths).
- **Zero** SSRF/path traversal/XSS (no network, no file I/O based on graph data, no HTML/JS).
- **Zero** secrets or weak crypto (only `hashlib.blake2b` for stable op qualnames — cryptographically secure and collision-resistant for this purpose).
- **Zero** auth/authz paths at all (this is an ML compiler backend, not a service).
- **No** tainted-data flows into kernel emission: shapes/dtypes come from `node.meta['val']` / FakeTensor (trusted by Dynamo) or `example_inputs`; op names are normalized via `_node_op_key` (lines 82-98) which only ever maps known ATen builtins.

**Only two minor non-exploitable notes** (not vulns):
- `<fx_to_tilelang.py:965-971>`: `content_hash` uses `repr(payload)` on `op_trace`. In a hypothetical malicious FX graph (e.g. attacker-controlled model with extremely long node names), this could bloat the hash input, but `blake2b(digest_size=8)` truncates safely and the registry is process-local. No DoS vector in real workloads (recompiles are rare and bounded).
- `<custom_op_wrapper.py:177-180>` + `<__init__.py:151-153>`: `_REGISTRY` + `_REGISTERED` globals use a lock only for the former. The registration flag race is theoretical (concurrent `torch.compile` on the same process is not a supported PyTorch contract) and cannot lead to code execution or privilege escalation.

**Bottom line**: Attacker controlling a model cannot turn this backend into RCE, data exfil, or kernel memory corruption. The POC is security-clean for production integration.

### 2. FX-to-TIR walking strategy critique → **Recommendation: keep hybrid (current design)**
Current design (`per-op handlers in ATEN_DISPATCH` + `_fusion_patterns.try_match` in `_materialize_subgraph`) is **the right choice** for this POC and for Phase 2.

**Why not pure pattern-matching (Inductor style)?**
- Pattern matching requires maintaining a separate subgraph rewriter that survives Dynamo’s many graph transforms. The current per-op walker re-uses the *exact same* `FXToTileLang` for both fwd and bwd graphs (see `aot_autograd_glue.py:144`) — huge win for correctness.
- Per-op handlers give **exact** shape propagation and early `UnsupportedFXOpError` (lines 104-108) before any TIR is emitted. This is the fail-fast the RFC wanted.

**When pure patterns would be better**: Phase 3+ when we want aggressive multi-op fusions (e.g. `layernorm_linear_gelu`). At that point we can extend `_fusion_patterns` (already present and used for `fused_linear` / `layernorm_linear` / `softmax_epilogue`) and keep the per-op handlers only for shape bookkeeping. **Hybrid wins** — current code already implements the best of both.

**Bug found here**: `<fx_to_tilelang.py:1225-1237>` — `try_match` is called, but `_emit_sequential_region` always raises `NotImplementedError`. This means **only** the `fused_linear` smoke pattern ever gets real TIR; everything else silently falls back to per-region eager replay (correct but defeats the point of the backend). Fix is trivial (see chunk 4 below).

### 3. Backward via aot_autograd — integration sketch (already 95% done!)
The current `aot_autograd_glue.py` is **correct and production-ready** for Phase 2.3.

**Exact flow** (PyTorch 2.11+ canonical):
```python
from torch._dynamo.backends.common import aot_autograd
backend = aot_autograd(
    fw_compiler=tilelang_fw_compiler,   # calls FXToTileLang + wrap_as_custom_op(is_backward=False)
    bw_compiler=tilelang_bw_compiler,   # same walker + is_backward=True
)
torch.compile(..., backend=backend)
```
- Same `FXToTileLang` walker works for both graphs because `_BWD_DISPATCH` is appended to `ATEN_DISPATCH` (lines 857-859).
- `wrap_as_custom_op(..., is_backward=True)` registers `tilelang::fused_xxx_bwd` and sets the autograd-disabled tag (option B from RFC).
- `make_boxed_func` contract is satisfied via the `_unboxed` wrapper (lines 157-163).

**No separate bwd pass needed** — the same walker + dispatch table handles it. The only missing piece today is full `_emit_*_backward` TIR bodies (currently they only shape-track).

### 5. Killer scenarios (when this backend silently produces wrong results)
Top 3 traps (all already documented in the RFC / aot glue comments):

1. **View aliasing** (`<aot_autograd_glue.py:46-53>`): Fused kernel always allocates fresh output buffers. If the FX graph contains a view that is later mutated in-place, the fused custom_op breaks aliasing. **Symptom**: correct numerics but downstream code sees stale data. Mitigation: add `mutates_args=()` + explicit view handling in Phase 3.
2. **Shape specialization mismatch** (`<fx_to_tilelang.py:169-176>`): If `example_inputs` shapes differ from runtime (dynamic shapes without Dynamo guards), the `content_hash` + custom_op cache returns a kernel for the wrong shape. **Symptom**: silent wrong results or crash. Current `_validate_graph` + FakeTensor path mostly prevents this.
3. **CUDA stream ordering / non-contiguous inputs**: TileLang kernels assume contiguous tensors (hard-coded `T.copy` patterns). If `torch.compile` passes a non-contiguous tensor without the `contiguous()` guard, kernel reads garbage. **Symptom**: NaNs or silent corruption on subsequent kernels. Fix: add `contiguous()` in the launcher or emit `T.copy` with proper strides.
