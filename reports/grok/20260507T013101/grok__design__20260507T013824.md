**Code Review: `poc/torch_dynamo/` POC for `torch.compile(backend="tilelang")`**

**Overall verdict (design-focused):** The architecture is clean and follows PyTorch 2.11+ idioms extremely well. Separation of concerns (registration → lowering → custom-op wrapping → AOT glue) is excellent. Lazy imports, content hashing for stable op names, and the declarative fusion table are all high-quality decisions. The POC correctly adopts **design (A)** (per-FX-subgraph `tilelang::fused_<hash>` qualname) — see justification below.

The **single biggest design flaw** is that the lowering path is incomplete in a way that violates the RFC §4 cache-resident fusion promise: `fx_to_tilelang.py:1316` (`_emit_sequential_region`) and the fallback machinery mean almost every real-world graph falls back to whole-graph eager replay (`_build_region_extern_launcher:1389`). This is the main source of "leaky abstraction" and duplicated `gm.forward` calls.

**Open design question — op naming**  
Stick with **(A)** (`tilelang::fused_<content_hash>` per subgraph).  
- Matches Inductor’s own fused-op strategy.  
- PyTorch 2.11+ has a process-local LRU on `torch._library.custom_ops._OP_REGISTRY`.  
- Guarantees perfect FakeTensor caching and stable AOTAutograd partitioning.  
- Aligns with TileLang’s existing `tilelang.jit.cached`.  
(B) would break fast-path FakeTensor handling and complicate the autograd-disabled tag used in integration #10.

**1. ATEN coverage gaps (Phase 2.2 priority order)**  
Current real emitters cover the easy wins. For inductor parity in LLM/training workloads the next 8 ops (by frequency in real `torch.compile` traces) are:

1. `t` / `transpose` (already in bwd dispatch — huge in gradients)  
2. `view` / `reshape` / `flatten` (shape manipulation — #1 most common)  
3. `expand` / `broadcast_to`  
4. `cat` / `stack`  
5. `pow`, `rsqrt`, `sqrt` (norm families)  
6. `clamp` / `clip`  
7. `dropout` (training)  
8. `threshold_backward` (the real ReLU backward that appears in smoke-test traces, not `relu_backward`)

Order by frequency: shape ops >> elementwise math >> reductions.

**2. FX-to-TIR walking strategy**  
Current hybrid (per-op handlers + `_fusion_patterns`) is the correct long-term design.  
- Per-op handlers give you a correct, minimal lowerer that never crashes.  
- Pattern matchers give you the high-value fusions (matmul+activation, layernorm+linear, softmax-epilogue) that actually deliver perf.  

**Critique of current implementation:**  
- `fx_to_tilelang.py:1225` only special-cases `fused_linear`; everything else hits the `NotImplementedError` → extern fallback.  
- This defeats the "register/shared-resident across FX boundary" invariant (RFC §4).  
- `_fusion_patterns.py` emitters are documentation-only stubs (`_emit_fused_linear:79` etc.).  

**Recommendation:** Keep the hybrid, but make `_emit_sequential_region` actually emit a chain of per-op TIR snippets (using the same `_alloc_intermediate_kind` heuristic already present). Pattern matchers stay for the 3–5 highest-ROI cases.

**3. Backward via aot_autograd**  
`aot_autograd_glue.py` is already the correct sketch.  

**Exact integration (PyTorch 2.11+ APIs):**
```python
# torch/_dynamo/backends/common.py
from torch._dynamo.backends.common import aot_autograd
# functorch.compile (or torch._functorch.aot_autograd)
from functorch.compile import make_boxed_func   # TODO: verify exact 2.12 path

backend = aot_autograd(
    fw_compiler=tilelang_fw_compiler,
    bw_compiler=tilelang_bw_compiler,
)
```
The **same** `FXToTileLang` walker works for both sides because:
- `ATEN_DISPATCH` already contains the bwd entries (`emit_mm_backward`, `emit_layer_norm_backward`, …) via the `setdefault` append at `fx_to_tilelang.py:857`.
- `wrap_as_custom_op(..., is_backward=True)` adds the `_bwd` suffix and relaxes the `requires_grad` guard.

`make_boxed_func` is required because `aot_autograd` expects the compiler to return a boxed `([tensors]) -> [outputs]` callable.

**`custom_op_wrapper.py:143` — `wrap_as_custom_op` (with minor cleanup)**
```python
def wrap_as_custom_op(
    artifact: FusedKernelArtifact,
    fx_signature: Dict[str, Any],
    *,
    is_backward: bool = False,
) -> Callable[..., Any]:
    suffix = "_bwd" if is_backward else "_fwd"
    op_qualname = f"tilelang::{artifact.name}{suffix}"

    with _REGISTRY_LOCK:
        if op_qualname in _REGISTRY:
            return _bind_runtime(_REGISTRY[op_qualname], artifact, is_backward=is_backward)

        from torch.library import custom_op, register_fake
        import torch

        @custom_op(op_qualname, mutates_args=())
        def _impl(args: Sequence[torch.Tensor]) -> Any:
            _check_no_grad(args, allow_grad=is_backward)
            full_inputs = list(args) + list(artifact.param_tensors)
            return artifact.launcher(*full_inputs)

        @register_fake(op_qualname)
        def _fake(args: Sequence[torch.Tensor]) -> Any:
            outs = [
                torch.empty(spec.shape,
                            dtype=_spec_to_torch_dtype(spec.dtype),
                            device=args[0].device if args else "meta")
                for spec in artifact.output_specs
            ]
            return outs[0] if len(outs) == 1 else tuple(outs)

        _impl._tilelang_autograd_disabled = True
        _impl._tilelang_is_backward = is_backward
        _impl._tilelang_artifact = artifact

        _REGISTRY[op_qualname] = _impl
        return _bind_runtime(_impl, artifact, is_backward=is_backward)
```

**5. Killer scenarios (silent wrong results vs eager)**  
Top 3 traps (in order of likelihood):

1. **View aliasing** (`custom_op_wrapper.py:195` + `mutates_args=()`): If the FX graph contains a view of an input that is later mutated, the custom op always materialises a fresh tensor. Result: correct numerics but broken aliasing downstream (e.g. `out.view(...)` + in-place op).  
2. **Forward path with `requires_grad=True`** before AOTAutograd capture: the guard in `_check_no_grad` fires correctly today, but any future removal without full aot_autograd wiring will produce wrong gradients.  
3. **Non-contiguous / strange strides**: TileLang kernels (especially the fused_linear one) assume contiguous inputs. If Dynamo passes a non-contiguous tensor the kernel reads garbage. Fix: add a `contiguous()` guard in the launcher or materialise a contiguous copy.

**Minor issues (quick wins)**  
- `fx_to_tilelang.py:1420` — the multi-region launcher is always `gm.forward`. This duplicates the fallback path.  
- Duplicated broadcasting logic (`_broadcast_shape`, `emit_matmul`, `_binary_elementwise`, `_emit_where`). Centralise in one `ShapeTracker` helper.  
- `LoweringContext` is doing too much (specs + op_trace + value_map). Consider extracting a pure `OpTracer` for the first pass.  
- `content_hash` includes `node.name` (not stable across traces). Use `node.target` + shape/dtype only.  

**Performance notes**  
- The current fused_linear path (`_emit_fused_linear_region:1280`) is already excellent (shared A/B tiles + fragment epilogue).  
- Everything else falls back → no perf win. Priority #1 is implementing `_emit_sequential_region` or more fusion patterns.  

**Summary recommendation**  
The skeleton is production-grade. The only thing preventing this from being a real backend today is finishing the sequential materialiser + adding the top 8 missing ops listed above. Everything else (naming, AOT glue, custom-op wrapping, hashing) is already solved correctly.

Great work — this is one of the cleanest Dynamo backend POCs I’ve seen. Ship the sequential emitter and you’ll have a genuinely usable TileLang backend.
