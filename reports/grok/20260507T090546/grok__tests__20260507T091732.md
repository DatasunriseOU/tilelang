**Remaining HIGH-severity issues (tests only)**

These are the only HIGH items left after the three waves. Everything else is either covered or low-priority.

1. **No coverage of the `tma_store` rewrite path**  
   - Location: `lower_tma_to_ptr_arith.cc:366` (`bool is_store = call->op.same_as(tma_store())`) through `RewriteTmaCall` (the `else` branch at ~370-380 that pulls `smem_handle = call->args[1]` and different `coords` indexing) and `BuildPointerArithCopy(..., is_load=false)` (~210-220: the `BufferStore(g_buf, BufferLoad(s_buf, ...), ...)` case).  
   - All 10+ test kernels use only `_build_tma_kernel` / `_build_tma_kernel_full` with `tma_load`.  
   - **Why HIGH**: The store path has subtly different arg parsing, offset math, and BufferStore direction. A regression here would silently corrupt global memory on Metal/HIP/CPU without any test catching it. (The load path is heavily exercised, but store is dead code from the test perspective.)

2. **No test for `tma_store_arrive` / `tma_store_wait` becoming no-ops**  
   - Location: `lower_tma_to_ptr_arith.cc:298-302` (the `if (call->op.same_as(tma_store_arrive()) || call->op.same_as(tma_store_wait()))` branch that returns `Evaluate(IntImm(0))`).  
   - **Why HIGH**: The comment in the header and the pass description explicitly state these become no-ops because the pointer-arith copy is synchronous. No test verifies they disappear (or become empty `Evaluate`) on non-Hopper targets. Easy to regress if someone touches `VisitStmt_`.

3. **Pipeline interaction only indirectly tested (swizzle/pragma_async_scope forwarding)**  
   - Locations:  
     - `inject_pipeline.cc:380-410` (`ContainsExplicitAsyncIntrinsics` now recognizes `"pragma_async_scope"` and `"pragma_tma_swizzle"`).  
     - `inject_pipeline.cc:400-420` (`AsyncCommitWaitAttrLowerer::VisitStmt_` for the `"pragma_tma_swizzle"` case that forwards to `For` annotation `"tl_tma_swizzle"`).  
     - `test_lower_tma_to_ptr_arith.py:220` (the `or "tl_tma_swizzle" in s` in `test_swizzle_distinguishability`).  
   - Current tests call **only** `LowerTMAToPtrArith()` (the `_lower` helper). The `or` clause was added in Wave-2 to anticipate the lowerer, but we never actually run the full sequence (`LowerTileOp` → `LowerTMAToPtrArith` → `InjectSoftwarePipeline`).  
   - **Why HIGH**: The whole point of the pragmas (see header comment in `lower_tma_to_ptr_arith.cc:80-100` and the `pragma_async_scope` / `tl_tma_swizzle` preservation) is to keep the rewritten copy eligible for software pipelining and Metal/HIP layout passes. Without a full-pipeline test we cannot guarantee the interaction survives future changes to either pass.
