**Bugs found (concrete, actionable, file:line):**

1. **`fp8_amax.py:line 312` (`fp8_pack_tilelang`)**: Empty-tensor handling (`if x.numel() == 0`) exists only for `fp8_amax_tilelang`. The subsequent `fp8_quantize_tilelang` call (and its kernel builder) assumes `n_elements > 0`. This is a latent crash on zero-size tensors when `clamp=True` (used by `ClampingFP8Packer`).  
   **Fix**: Add the same fast-path guard in `fp8_quantize_tilelang` (or hoist it into `fp8_pack_tilelang` before calling quantize). Matches the Triton reference behavior.

2. **`fp8_amax.py:lines 158, 218`** (`globals()` update inside `make_*_kernel`): The pattern works but is fragile and not present in the style-guide reference `fp8_vecmat_path_c.py`. If a future caller imports the module and calls the builder twice with different shapes, the global mutation can leak between JIT caches.  
   **Fix**: Pass the constants as closure variables or use `T.constexpr` (TileLang DSL supports it — see `tilelang/language/__init__.py` and the vecmat sibling).

3. **`fp8_activations.py:line 650`** (`FP8ActivationPacker.pack`): The `has_tilelang and tilelang_supports(tensor.device)` guard is correct, but `tilelang_supports` (overridden at import) still calls the duplicated `_tilelang_available` check on every hot-path tensor. Minor, but the original `tilelang_supports` shim in the except block returns `False` without import.  
   **Fix**: Make the shim call the real function (already done on success path).

4. **`test_fp8_amax_tilelang.py:line 55`** (Triton parity test): Skips correctly on non-CUDA, but the Metal path only tests vs. `torch.abs().amax()`. No test exercises the full `fp8_pack_tilelang` round-trip with `clamp=True`.  
   **Fix**: Add one bf16 + clamp test case (mirrors the `fp8_vecmat_path_c` test style).

5. Minor style inconsistency: `fp8_amax.py` uses `T.cast(..., "float8_e4m3")` while the Triton reference and `fp8_vecmat_path_c.py` consistently use `float8_e4m3fn` / `tl.float8e4nv`. Numerical parity holds, but keep the exact string for future e5m2 support.

No OOB reads, no device mismatches, no missing `contiguous()` calls (already present), and the Metal target string (`fp8_amax.py:line 105`) matches the vecmat sibling exactly.

**Performance improvements (prioritized, concrete):**

1. **Already excellent**: `@lru_cache(maxsize=64)` on `_amax_kernel_for` / `_quantize_kernel_for` (`fp8_amax.py:lines 280, 290`) and the shape-specialized PrimFunc approach perfectly mirrors `fp8_vecmat_path_c.py`. JIT cost is paid once per (N, dtype, target).

2. **High-impact suggestion**: The two-pass design (amax → host sync → quantize) is explicitly noted as deferred. On Metal this costs an extra device sync per checkpointed activation. Future fused kernel (single `T.Kernel` with internal `T.reduce_max` + broadcast of the scalar) would eliminate it — exactly as the original Triton path comment suggests. TileLang’s `T.atomic_max` + shared memory already makes this straightforward.

3. **Amax kernel micro-opt** (`fp8_amax.py:lines 170-185`): Two separate `T.Parallel(BLOCK)` loops (load → abs → reduce). Fuse the abs into the load loop (one `Parallel` + `T.reduce_max` directly on `float32` view). Saves one full block-wide pass on memory-bound tensors. TileLang’s `T.reduce_max` handles the cast/abs inline (see DSL in `tilelang/language/__init__.py`).

4. **Block size tuning**: Hard-coded `_FP8_AMAX_BLOCK_SIZE=1024` / `THREADS=128` works on both CUDA/Metal but is suboptimal on Apple Silicon (SIMDgroup=32). Make it device-aware (query `torch.backends.mps` or TileLang target) or expose as a parameter like the vecmat kernel does (`outputs_per_block`, `reduce_threads`).

5. **Quantize kernel**: The clamp is already fused (`T.max`/`T.min`). Perfect. The `if gi < N` guard is necessary for the last block — no further win here.
