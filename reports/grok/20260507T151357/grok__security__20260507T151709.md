### Security-relevant findings (races + validation + boundary assumptions)

1. **Race condition in FP8 AMAX not fixed (worsened availability exposure)**  
   File: `fp8_amax.py` (module globals `_FP8_AMAX_LOCK`, `N`, `BLOCK`, `DTYPE` + kernel launch site).  
   Wave-11 cleanup (d6c4772 + 55d7346 + 1a5f19ba) explicitly deferred per-signature locking to wave-12. Globals remain shared.  
   **Concrete attacker scenario**: Multi-threaded inference server (vLLM-style or TorchServe with concurrent user requests / multiple models). Attacker issues two simultaneous FP8 quant calls with different signatures (e.g., fp8_e4m3 vs fp8_e5m2, or different BLOCK sizes). One thread overwrites globals while the other reads → kernel launched with wrong N/BLOCK/DTYPE or corrupted AMAX value. Result: NaN/Inf scaling factors → downstream matmul overflow/underflow or GPU kernel crash. In a shared service this is a clean availability DoS (one thread starves others while holding the global lock). Same class as the still-open lock-DoS (3c) from backlog. No regression vs wave-10, but the “cleanup” commit makes the race more visible/documented without mitigating it.

2. **reduce_prod lowering now strictly rejects non-pow-of-2 reducing_threads (good for safety, but static_assert may create new compile-time DoS surface)**  
   Files: lowering path `MakeInitValue` (both scalar + batched), `cuda/reduce.h:??`, `hip/reduce.h:??` + static_assert.  
   ed7c6457 adds `ICHECK` + flips xfail→pass.  
   **Concrete attacker scenario**: User-controlled model (ONNX/TorchScript import or dynamic shape in a training loop) reaches reduce_prod lowering with non-power-of-2 thread count (possible via certain reduction sizes or custom ops). Previously might have produced wrong results / OOB; now compile-time rejection. If the lowering is triggered at runtime (e.g., first forward pass of a JIT model) and the static_assert is hit in a release build, the entire worker process aborts. In a multi-tenant serving environment this is a DoS vector via crafted model. Backlog item “reduce_prod runtime fix vs static_assert” is still open → current state trades silent wrongness for loud crash. No new injection path, but stricter enforcement on tainted shape-derived values is a net security win.

3. **DSA TOPK=0 now explicit ValueError (solid input validation improvement, no regression)**  
   File: DSA code handling `topk_indices.shape[2]==0 + sparse_loss=True` (exact line not in commit summary, but inside the (a) change set d6c4772).  
   **Concrete attacker scenario**: Attacker controls `k` (top-k hyperparam) or input tensor shape that produces 0 valid indices + `sparse_loss=True`. Pre-fix this could reach index math or sparse ops with shape[2]=0 → potential OOB read/write or NaN propagation in loss. Now cleanly rejected before kernel launch. No tainted-data bypass introduced.

4. **_detect_storage_overlap() now catches as_strided siblings (prevents silent aliasing → data corruption)**  
   File: wherever `_detect_storage_overlap` lives (likely tensor view utils).  
   55d7346 improvement.  
   Good: previously two `as_strided` views that overlap in storage but have different base pointers could alias undetected → heisenbugs or memory corruption under concurrent ops. Now caught. Passes Torch 2.x M4 Max. No security regression; actually reduces attack surface for “write via one view, read stale data via sibling” in multi-threaded forward/backward passes.

5. **Metal atomic_max NaN pre-filter (minor improvement, but NaN→0 semantics need scrutiny)**  
   File: `fp8_amax.py:386` (T.if_then_else(v==v, v, 0) before `T.atomic_max`).  
   52f1770 + 910756c.  
   Prevents NaN propagation on Metal (where fp atomic_max with NaN is implementation-defined).  
   **Edge case**: If input tensor legitimately contains NaNs (adversarial data or upstream bug), amax now underestimates (treats NaN as 0). Result: too-small scale factor → later FP8 matmul overflows. Not a crash, but model integrity issue. Not worse than before; just makes behavior explicit. No other backends appear to have equivalent filter yet.

### Verify questions

1. **Wave-11 fixes correct? Any regressions?**  
   Yes correct on their stated goals. No regressions visible from commit descriptions. NaN filter, TOPK=0 guard, alias detect, and pow2 enforcement all tighten safety. The only “regress” is the explicit documentation that per-sig lock is still missing (makes the race easier to hit in testing).

2. **Wave-10/wave-11 backlog still open?**  
   Yes:  
   - lock-DoS (3c) — unchanged, still global.  
   - reduce_prod runtime fix vs static_assert — still open (ICHECK + static_assert is compile-time only).

3. **Anything new at this layer that all 3 LLMs would miss? (“Boundary assumption” 4th-category bugs)**  
   Two subtle ones:  
   - `topk_indices.shape[2]` access assumes the tensor always has rank ≥3 and is not None/empty before the new check. If a call site passes a rank-2 tensor or uninitialized index tensor under certain shape edge cases, you get IndexError or UB before the ValueError. (Boundary assumption that “topk always returns at least 3D”.)  
   - NaN pre-filter `v==v` assumes floating-point input. If ever called on integer tensor (future refactor), it becomes a no-op or wrong. Metal-specific path only; other GPU backends silently differ.  
   - reduce_prod pow2 check assumes all legitimate reductions are power-of-2 at lowering time. Dynamic shapes that become non-pow2 only at runtime (e.g., batch=variable) now fail compile instead of running with previous (possibly incorrect) kernel.

4. **Test coverage gaps in the wave-11 changes?**  
   - Concurrent FP8 AMAX calls with varying signatures/dtypes (race repro).  
   - Non-power-of-2 `reducing_threads` error path (now expected to raise).  
   - Metal-only NaN-inf inputs to AMAX (before/after pre-filter).  
   - `as_strided` sibling overlap cases (both the new detection and any intentional overlap that should be allowed).  
   - TOPK=0 + `sparse_loss=True` with rank <3 tensors or k=0 from different code paths.  
   - reduce_prod with dynamic shapes that only become non-pow2 at runtime.

**Summary**: Wave-11 is a net security improvement on input validation and aliasing, but leaves the FP8 global race (and its DoS potential) untouched and documents it for wave-12. No new high-severity vulns introduced. The remaining boundary assumptions around tensor metadata are the highest-risk items for a production serving environment.
