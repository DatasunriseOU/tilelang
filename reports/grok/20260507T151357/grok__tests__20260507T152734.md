### 3. New “boundary assumption” 4th-category bugs that all 3 LLMs would miss?
Three subtle ones introduced exactly by Wave-11 (the pattern you referenced from meta’s previous findings):

- **fp8_amax.py:386 NaN filter boundary**: assumes `v==v` behaves identically for all FP8 variants on Metal (including subnormals, -0.0, and NaN payload bits). Attacker scenario: feed FP8 tensor with *only* quiet-NaN payloads that survive the `==` test differently than on CUDA; amax silently becomes 0 instead of propagating. (Metal FP8 encoding edge not covered by the if_then_else.)
- **DSA TOPK=0 + sparse_loss=True ValueError path**: the shape[2] check is added *after* earlier tensor construction. Attacker scenario: dynamic shape where `topk_indices.shape` is constructed with dim2=0 but the preceding ops already produced NaN before the guard (e.g., empty topk indices fed to loss). The ValueError fires too late in some call paths.
- **_detect_storage_overlap() + as_strided siblings**: now catches siblings, but the check assumes Torch 2.x `as_strided` storage layout is the *only* aliasing source on M4. Attacker scenario: non-M4 device + torch 2.x view created via `view()` + manual stride manipulation that produces overlapping storage *not* flagged as “as_strided sibling”. UB slips through on non-Apple hardware.

These are exactly the “we assumed the new guard covers the entire boundary” class of bug.
