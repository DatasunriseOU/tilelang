### 2. Wave-10/wave-11 backlog still open?
**Yes — both items remain open:**

- **lock-DoS (3c)**: Explicitly called out in the wave-11 cleanup commit as “_FP8_AMAX_LOCK per-signature — NOT done”. The module-globals (N/BLOCK/DTYPE) are still shared. This is the exact root of the DoS risk.
- **reduce_prod runtime fix vs static_assert**: The static_assert (cuda+hip reduce.h) and ICHECK (MakeInitValue) are compile-time only. The backlog note implies a runtime path (or future dynamic thread config) still exists that the enforcement does not cover. The duplicated checks (see below) make it easy for a new lowering path to bypass one of them.

### 3. New “boundary assumption” 4th-category bugs (the kind all three LLMs usually miss)
These are the implicit “we assumed X would never happen” cases that only surface after the wave-11 tightening:

- **fp8_amax.py:386 NaN pre-filter assumption**  
  Assumes *every* value fed to atomic_max is either a normal FP8 number or a quiet NaN that can safely become 0.  
  **Concrete attacker scenario**: all-NaN input tensor → AMAX now returns 0 instead of NaN (or propagating NaN). If downstream scaling expects NaN to survive (common in some FP8 training recipes), this silently changes semantics *only on Metal*. Cross-backend divergence introduced.

- **MakeInitValue (both scalar + batched paths) + reduce.h**  
  Now assumes reducing_threads is *always* set *before* MakeInitValue is called *and* is pow-of-2.  
  **Boundary**: a new pass that generates reduce_prod with dynamic thread count (e.g. from a shape symbol) hits ICHECK at lowering time. Previously it would have produced (incorrect but non-crashing) code; now it fails fast. The static_assert in reduce.h only protects the CUDA/HIP codegen path — any new backend (or future Metal reduce) silently regresses.

- **DSA TOPK=0 + sparse_loss=True** (the ValueError path added in d6c4772)  
  Assumes shape[2] *always exists* on topk_indices.  
  **Boundary**: batch=0 or a 2-D topk tensor (no dim-2) + sparse_loss=True → index error *before* the new ValueError, or wrong error message. The commit only hardened the shape[2]==0 case.

- **_detect_storage_overlap() as_strided siblings**  
  Now tighter, but still assumes Torch’s as_strided view metadata is the *only* source of aliasing.  
  **Boundary**: future Torch version (or a custom tensor subclass) that creates aliasing via other means (e.g. torch.Tensor._make_subclass + custom storage) will again be missed until the next M4-style patch.

These are classic 4th-category bugs: the fixes tightened one assumption while exposing the next layer of “we never considered …”.

### 4. Test coverage gaps in the wave-11 changes
- No concurrency test for multiple *different signatures* hitting the global _FP8_AMAX_LOCK (the exact lock-DoS scenario).
- No negative test for non-pow-of-2 reducing_threads in *every* lowering path — only the xfail that was flipped.
- No test for all-NaN or NaN+Inf mixes in Metal AMAX path (fp8_amax.py:386).
- No Torch 2.x as_strided test with *zero-size* or *negative stride* siblings.
- No test that exercises the batched vs scalar MakeInitValue paths with identical thread counts (the duplicated enforcement hides divergence).

### Design & architecture findings (prioritized by severity — prefer-simplify first)

1. **Leakiest module: global state in FP8 AMAX (fp8_amax.py module-level _FP8_AMAX_LOCK + N/BLOCK/DTYPE)**  
   Violated abstraction: “AMAX is a pure per-kernel operation”.  
   Reality: module-global mutable state shared across *all* calls and *all* signatures.  
   Awkward coupling: every fp8_amax call site is implicitly coupled to the same globals.  
   Missing extension point: no clean way to add per-signature locking without touching the globals again.  
   **Concrete attacker scenario**: two threads calling fp8_amax with different (N, BLOCK, DTYPE) tuples in a tight loop → lock contention / memory growth / DoS (exactly backlog item 3c).  
   **Simplify suggestion**: kill the globals. One tiny AMAXContext class (or even a dict of locks keyed by (N, BLOCK, DTYPE) tuple with weakref) would eliminate the entire race surface and the wave-12 todo. This is the single highest-leverage design fix.

2. **Duplicated pow-of-2 enforcement (MakeInitValue scalar path + batched path + static_assert in cuda+hip reduce.h)**  
   Classic DRY violation. The same contract is restated in three places.  
   Any future change (e.g. supporting non-pow2) must touch all three → high maintenance cost and easy divergence.  
   **Simplify suggestion**: single early validator (e.g. `validate_reduce_threads(reducing_threads)`) called once in the public lowering entry point. Let the backends rely on that instead of repeating ICHECK/static_assert.

3. **Backend-specific NaN hack at fp8_amax.py:386**  
   Leaky abstraction: NaN semantics are now splintered across backends instead of living in a common FP8AtomicMax or NaNPreprocess trait.  
   The T.if_then_else is the canonical “quick hack” that grows into a forest of similar hacks.  
   **Simplify suggestion**: lift the NaN->0 (or NaN-propagate) logic into a reusable TIR primitive used by *all* backends. Then Metal, CUDA, HIP, CPU all get identical behavior by construction.

4. **Tight Torch coupling in _detect_storage_overlap()**  
   The as_strided sibling detection is now correct for current Torch 2.x but is a maintenance magnet.  
   **Simplify suggestion**: if Torch aliasing rules are stable enough, expose a small TorchTensorAliasChecker utility instead of burying the logic inside the core storage overlap detector. Makes the dependency explicit and easier to update.

**Overall architecture health**: Wave-11 cleaned up surface crashes but left (and in one case documented) the deeper structural problems — globals, duplicated enforcement, backend-specific hacks, and implicit boundary assumptions. The pattern is consistent: each wave fixes the *symptom* while the *design debt* (leaky modules, missing extension points) stays or grows.  

The two highest-impact, simplest changes you can make for wave-12 are:
- Remove the module globals in fp8_amax.py (per-signature lock or context object).  
- Centralize the pow-of-2 check and NaN preprocessing.

Everything else (TOPK=0, aliasing) is already nicely contained. These two would eliminate the lock-DoS backlog item and prevent the next wave of duplicated-hack bugs.
