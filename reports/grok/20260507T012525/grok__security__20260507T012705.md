### 3. PtrAnalysis driver sketch (`ptr_analysis.py` stub)

**Python-driven flow (recommended, no full C++ rewrite needed initially)**:
1. Load TTIR module via `mlir-python-bindings` (`mlir.ir.Module.parse(ttir_text)`).
2. Run registered MLIR pass `tts-ptr-analysis` (or invoke `mlir::tts::PtrAnalysis::rewriteOp` if exposed).
3. Walk resulting `tts.make_tptr` ops → convert to TileLang `ptr(...)` / `make_tensor` (`language/__init__.py:30`).
4. Emit TileLang TIR via standard `tvm.script.parser.tir` builders (already imported in language).

`mlir-python-bindings` **are sufficient** for pass manager + walk; only a thin C++ registration shim (exposed as a single MLIR pass) is needed if `PtrAnalysis::rewriteOp` is not already registered. No heavy C++ required for POC.

### 5. Killer ambiguity

**The one design choice that kills the whole approach if wrong**: Hooking at **TTIR (post-AST, pre-layout assignment)** vs. lowering first to TTGIR.

**Right answer (per RFC §5)**: Hook at TTIR + reuse `microsoft/triton-shared` `PtrAnalysis` is correct. It gives you clean stride/offset recovery *before* Triton does its own layout, letting TileLang’s `LayoutInference` + `LowerTileOp` take over cleanly. If you hook later (post-TTGIR), you lose the PtrAnalysis benefit and the mapper becomes a fragile TTGIR↔TileLang translation layer. This choice is the single point that makes the entire unified-fused-kernel strategy viable.
