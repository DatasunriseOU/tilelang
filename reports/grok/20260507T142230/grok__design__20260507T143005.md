**WAVE-10 FINAL REVIEW (Grok + Lucas + Benjamin consensus)**

All three wave-10 fixes are **correct and regression-free**:

1. **DSA zero-size guard** (`dsa_splitk_indexer_loss.py:650-670`): early-out before any `T.ceildiv` / kernel build. Returns 0-d scalar exactly matching the Triton contract. Solid.
2. **TMA i64 offsets** (`lower_tma_to_ptr_arith.cc:280-300` + `BuildPointerArithCopy`): `kIdx=Int(64)` everywhere + explicit comment addressing meta's false-positive. Locked by existing test. Good.
3. **reduce_prod contract** (`reduce_op.py:280-320`, `reduce.h:80-100`): documented MulOp identity-pad requirement + xfail test. Wave-10 intent achieved.

**reduce_prod contract is *not* sufficient today** (documentation-only). The real fix (C++ `MakeInitValue` in `src/op/reduce.cc`) is still wave-11. Callers that forget to pad inactive lanes (or direct `tl.tileop.reduce(mul)` users) still get silent wrong results / NaN attacks on non-warp-multiple dimensions. The Python `reduce_macro` should enforce the pad (or at least assert) until the lowering is fixed.

**Remaining un-addressed meta findings from prior waves (the persistent smells):**
- `_expose_to_globals` hack (`fp8_amax.py:60-110`) is still live and duplicated in spirit by DSA's closure-heavy kernel builders. This is the single biggest architectural wart.
- Target/shape/ Metal-budget logic lives in Python kernel factories instead of TileLang engine/target config.

### Design & Architecture Issues (Concrete, Actionable)

**1. Massive duplication / leaky per-kernel modules** (core violation of "unified fused-kernel pipeline" claim)
- `_tilelang_available`, `*_path_c_status`, `tilelang_supports*`, `_resolve_target`, `_TORCH_DTYPE_TO_TL`, `_resolve_in_dtype` are copy-pasted between `fp8_amax.py:140-220` and `dsa_splitk_indexer_loss.py:300-400` (plus `_resolve_in_dtype` again at ~580).
- Block picking / bucket logic (`fp8_amax.py:200-250`) vs. `_metal_block_overrides` + `_block_constants_for_target` + `_can_use_q_cache_v5_tiled` (DSA) vs. future kernels.
- JIT caches + locks duplicated (`_amax_kernel_for`/`_quantize_kernel_for` vs. `_stage*` caches).
- **Root cause**: each "Path C" file is a self-contained monolith. Violates DRY and makes adding a new kernel (e.g. fp8 matmul) painful.

**Recommendation (simplifies everything)**: extract to `cppmega_mlx.nn._tilelang._common_support.py` (or `kernel_factory.py`) with a `TileLangPathCSupport` class + registry. One place for support checks, dtype mapping, target resolution, and a unified `@lru_cache` factory wrapper.

**2. Fragile parser workarounds & global mutation** (leakiest abstraction)
- `fp8_amax.py:60-110` (`_expose_to_globals` + `_FP8_AMAX_LOCK:30`): mutates module `__globals__` so `typing.get_type_hints` inside `@T.prim_func` sees `N`/`BLOCK`/`DTYPE`/`FP8_MAX`. DSA avoids the explicit hack but still relies on the exact same closure resolution for `COMPUTE_INDEX`, `SCALE`, `SPARSE`, etc. inside the nested `@T.prim_func` bodies.
- This is *not* a small hack — it's a fundamental leak between TileLang's Python decorator parser and our DSL style. The lock only papers over the race; it doesn't fix the underlying coupling.

**Action**: Upstream a proper `localns` / closure support to TileLang's `@T.prim_func` (or switch to string-based PrimFunc emission for complex kernels). Until then, document as "known technical debt" and gate new kernels behind it.

**3. Target-specific tuning leaked into DSL** (over-engineering + tight coupling)
- `dsa_splitk_indexer_loss.py:220-280`: `_metal_block_overrides` with AH-dependent `BLOCK_SQ` halving (register budget math for 32 KB threadgroup). Called from `_block_constants_for_target` and wave-5/8 Q-cache logic.
- `fp8_amax.py:200-250`: `_pick_block_size` + `_BLOCK_SIZE_TABLE` + power-of-two bucketing.
- These decisions belong in the *lowering* (TileLang engine / target config) or a declarative `BlockConfig` dataclass, not scattered Python kernel builders. Current design makes the "single TileLang source" claim false — Metal vs. CUDA divergence is Python-level, not lowering-level.

**Simplification**: Push into `TileLang` target attrs or a small config registry. The Python layer should only pick "default" vs. "metal-tuned" once.

**4. Custom op wrapper complexity** (`custom_op_wrapper.py`)
- Good: `FusedKernelArtifact` + multi-region support + `_REGISTRY` idempotency (RFC §3).
- Overly clever: n_outputs=1 vs. >1 branching in `_impl`/`_fake` (`lines 140-200`) + `_ensure_contiguous_inputs` side-effects + global `_CONTIGUITY_WARN_SEEN` + many `_tilelang_*` attrs hung on the callable.
- The `is_backward` flag + autograd-disabled tag is a necessary integration #10 hack, but the whole thing feels like it grew organically rather than from a clean "Torch backend contract" abstraction.

**Minor simplification**: Normalize launcher return to always be `tuple` (even for single output) and drop the special-case branches.

**5. C++ lowering & reduce layer**
- `lower_tma_to_ptr_arith.cc:450-520`: explicit `tma_load_im2col` WARN + no fallback is the *correct* conservative design (better than silent wrongness). But the `DecodedDesc` + `BuildPointerArithCopy` dance (with synthetic `LetStmt` Buffers for pipelining) is dense and tightly coupled to TMA encoding in `copy.cc`.
- `reduce_op.py:290` (still has the old `reduce_prod` warning) + `reduce.h:80-100` (MulOp comment): contract is documented, but the Python macro should enforce the identity pad until wave-11 lowering.

**6. Minor clarity / maintainability**
- Heavy "Wave-N #M (grok/meta review ...)" comments everywhere (`fp8_amax.py:10-50`, `dsa_splitk_indexer_loss.py:10-30`, etc.). Useful for history but clutter public API docs and make the files feel like living PR threads rather than stable code.
- Global mutable state (`_SCATTER_SCRATCH_CACHE:30-60`, `_REGISTRY`, `_CONTIGUITY_WARN_SEEN`, locks) is defensively correct but couples modules to process lifetime.
- `fp8_amax_tilelang:510-530` ad-hoc `use_exact` heuristic (1.5× inflation threshold) is a clever but leaky perf knob exposed at the public API boundary.

### Performance Notes (design-tied)
- DSA scatter scratch cache + Q-hoist wave-5 are excellent.
- FP8 bucket vs. exact is a reasonable trade-off, but the heuristic could be a simple policy object.
- No obvious hot-path regressions from wave-10 changes.

**Biggest simplification opportunity**: Centralize the TileLang Python scaffolding (`_common_support.py` + factory) and kill the globals/parser hack. This would make the "Path C" pattern actually maintainable as the number of fused kernels grows (FA, fp8 matmul, etc.).

The overall architecture ("single TileLang source for CUDA + Metal replacing Triton") is the right long-term bet; the current implementation pays the tax of Python-level target hacks and parser workarounds. The wave-10 fixes are clean — the persistent smells are the ones listed above.

No new 4th-category bugs jumped out that all three of us missed together. Ready to ship once the reduce_prod enforcement and common-support extraction land (or are explicitly deferred).
